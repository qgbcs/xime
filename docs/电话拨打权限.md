现在现象基本对上了：**同一个安装包、同一个 UID，仅仅把电话权限拒绝再开启后，Android 返回的实际权限状态就从拒绝变成了允许，Telecom API 也随即恢复。**这说明问题不在 MQTT 或 Chaquopy，而在设备当时保存的电话权限状态。

我通过 MQTT 对比了操作前后的状态：

| 检查项 | 重新切换权限前 | 重新开启后 |
|---|---|---|
| 包名、版本、UID | `com.qgb.xime`、`20260918`、`10423` | 完全相同 |
| `CALL_PHONE` 拨打电话 | 已授权 | 已授权 |
| `READ_PHONE_STATE` 读取手机状态 | **未授权**，AppOps 为拒绝 | **已授权**，AppOps 为允许 |
| `READ_PHONE_NUMBERS` 读取电话号码 | 已授权 | 已授权 |
| `getCallCapablePhoneAccounts()` | 抛出缺少 `READ_PHONE_STATE` 的安全异常 | **成功，返回 2 个电话账户** |

因此，先前“权限页都显示已授权”与系统 API 检查结果确实发生了矛盾。切换电话权限后，包管理器的权限检查和 AppOps 状态一起变为允许，紧接着同一 Telecom API 就成功了。这强烈说明：**设备此前实际保留了 `READ_PHONE_STATE` 的拒绝状态；重新切换权限触发了系统重新写入或同步该权限状态。**具体是 ROM 权限管理页状态与底层权限记录短暂不同步，还是权限组切换时一并刷新了相关 AppOps，目前仅凭远程结果无法区分，但“旧状态未正确同步、切换后刷新”与观测完全吻合。

这也解释了旧版本与现在看起来不一致：拨电话的 `CALL_PHONE` 和读取可拨号账户的 `READ_PHONE_STATE` 是不同权限。旧版本可能只执行拨号，所以 `CALL_PHONE` 获准就够了；新代码如果先调用 `getCallCapablePhoneAccounts()`，则额外需要 `READ_PHONE_STATE`。在恢复授权前，即使界面显示“拨打电话”已开启，账户查询仍会被系统拒绝。切换电话权限后，当前账户查询已实际通过并返回两个 SIM 账户。

此前修正的批量申请去重问题仍然有意义：它可以避免权限页批量申请时漏掉某些权限；但它不能替系统修复已经保存的拒绝状态。**这次直接让设备恢复正常的是你重新切换了电话权限。**
